# SKYFALL v1.0.1 — Phase 5 Architecture Design

**Date:** 2026-11-20
**Phase:** Phase 5 — Requirements traceability and implementation design
**Mode:** Documentation output only. No application source, database, config modified.
**Inputs:** Phase 1 architecture map, Phase 2 comparison, Phase 3 memory audit, Phase 4 spec analysis, traceability matrix.

---

## 1. Design principles (inherited from spec §1, §12)

1. Modular monolith — no service extraction, no Kubernetes/microservices.
2. Preserve working functionality; evolve based on evidence.
3. Never invent functionality; reuse existing abstractions; avoid duplicate services.
4. Prefer small, coherent, reviewable modifications traceable to a requirement.
5. Data protection policy (15 rules) is non-negotiable.
6. No broad refactoring without a concrete requirement.

---

## 2. The 17 design areas

### DA-1. System topology (modular monolith)
- Single Qt desktop process (PySide6) + one MCP child process (stdio) — unchanged topology.
- No HTTP service in production path; `backend/api.py` remains dormant unless a concrete requirement activates it (decision required).
- Modules: `app/desktop`, `integrations`, `memory`, `skyfall_workspace`, `skyfall_cloud`, `skyfall_mcp`, `configuration`.
- DAG preserved (no cycles).

### DA-2. UI architecture
- Single `MainWindow` owns all pages (11 `NAV_ITEMS`); no new top-level windows except dialogs.
- Theme via `app/desktop/theme.py` (`APP_STYLESHEET`); Kiro/graphite palette retained unless visual QA rejects.
- Add loading/empty/error/success states to every page (SP-003).
- Responsive splitters/scroll areas at compact sizes (SP-004).
- Remove hardcoded demo data from production paths (SP-005/006).
- Consistent interaction patterns across pages (SP-008).
- Preserve 5 data tables' columns/mapping; decide sorting/filtering scope (SP-010).
- Reports page: either implement centralized library or keep per-page XLSX open (decision).

### DA-3. Backend service boundaries
- Keep direct in-process module calls (current pattern); introduce shared interfaces only where a concrete requirement demands (SP-013, SP-018).
- Dormant services disposition: wire with callers, or document deferral, or remove from scope (SP-012). No deletion without approval.
- `backend/api.py`: activate only if a requirement needs HTTP; otherwise document as dormant.

### DA-4. Memory architecture (3 layers, 3 stores)
- Conversation memory: `skyfall.db` (`%LOCALAPPDATA%\SKYFALL\data\`), WAL, RLock.
- Persistent/project memory: `workspace_index.db` + `Data_Memory/`.
- Session memory: Copilot SDK transcripts keyed by `copilot_session_id`.
- `Data_Memory/skyfall_memory.sqlite3`: intent pending (decision 6). Until decided, treat as read-only archival; no migration into runtime.
- Markdown memory files: hand-maintained; never overwrite; any DB↔Markdown sync preserves manual authorship.

### DA-5. Database ownership and access
- Two runtime SQLite stores: `skyfall.db` (conversations), `workspace_index.db` (workspace index).
- `Data_Memory/skyfall_memory.sqlite3`: orphan artifact (zero code refs) — read-only until decision 6.
- Connection management: per-call connection behind RLock (conversations); WAL + busy_timeout=20000 (both). Workspace manager has no RLock — add if concurrent scan races are observed.
- No cross-store transactions; each store owns its consistency.

### DA-6. Persistence and migration framework
- Introduce a versioned migration mechanism (custom or Alembic) with `schema_version` tracking (SP-029).
- Mandatory 9-step protocol per migration: identify consumers; capture schema; backup; test on copy; verify integrity; compare counts/identifiers; verify relationships/constraints; document rollback; obtain explicit approval before irreversible change.
- Never delete/replace/drop without approved migration (SP-032).
- Preserve identifiers (UUID conversation ids, `copilot_session_id = "skyfall-{hex}"`, message autoincrement) (SP-030).
- Backup/restore: wire `backup_database` with restore counterpart; redact exports (SP-034, H-02).

### DA-7. AI and agent behavior
- Copilot SDK session + permissions unchanged (byte-identical since v0.9.2); 20-tool MCP allow-list; 180 s prompt timeout.
- MCP child process boundary preserved (clean stdio; stdout reserved for protocol).
- Agent orchestration per spec §3 (12 specialists, selection rules, 9-field delegation, reasoning allocation).
- No multi-step orchestration beyond current single-turn worker unless a requirement demands (module 1 scope pending decision 1).

### DA-8. Integrations
- Preserve all: Copilot SDK, MCP stdio, Azure CLI, Power Platform REST, MSAL, PAC CLI, openpyxl, httpx.
- Auth source: decision 10 pending (MSAL canonical vs Azure CLI current). Until decided, both code paths remain; do not remove either.
- Power Platform: keep both Environment Management API (MSAL path) and Power Apps API (Azure CLI path) branches.
- No new external dependencies without justification (SP-013).

### DA-9. Security architecture
- At-rest: conversation messages plaintext (H-01) — document posture; encryption is a candidate improvement, not mandated by spec. Decision needed before implementing.
- Redaction: extend `redact_sensitive_text` (api_key, connection_string, subscription_key, …) (M-04); redact before persist/export (H-02, M-01).
- Secret detection: add high-entropy detection to workspace analyzer (M-02).
- Profile registries: file locking on atomic replace (M-03); cleanup orphaned Azure CLI config dirs on removal (M-05).
- `Data_Memory/`: gitignore `*.sqlite*`; scrub sensitive artifacts (M-06).
- WAL sidecar checkpoint discipline (L-01); encrypted backups (L-02); metadata minimization (L-03/L-04).
- Security tests in `tests/security/` (currently empty) (SP-050).
- No credentials/secrets in logs/reports (SP-051).

### DA-10. Performance
- Baseline: 100-row preview caps (Azure Function Apps, Flow Inventory), 20k files/2 MiB workspace scan caps, 500 conversation list cap, 200 message retrieval (no pagination).
- Performance tests to establish baseline (SP-055).
- No premature optimization; profile before changing caps.

### DA-11. Reliability
- WAL + busy_timeout + transactional rollback in both stores (preserve).
- Global exception handling: add `sys.excepthook`/Qt message handler for crash reporting (currently absent).
- Lifecycle: closeEvent waits for workers; refuse close if running (preserve).
- Never claim test success without evidence (SP-061).

### DA-12. Configuration
- Env vars: `LOCALAPPDATA`, `SKYFALL_ROOT`, `SKYFALL_TEST_MODE`, `SKYFALL_POWERPLATFORM_CLIENT_ID`, `AZURE_CONFIG_DIR`, `PYTHONPATH`, `PYTHONUTF8`, etc.
- `configuration/capabilities.json`: 20-tool catalogue, strictly validated, version 1.
- Version markers: reconcile `0.9.2` (app code) vs `1.0.1` (spec) — single source of truth (SP-016).
- No YAML/keyring/pydantic-settings at runtime despite declarations; remove or activate deliberately.

### DA-13. Testing strategy
- Environment: Python 3.13 venv outside repo/OneDrive (recommended, not yet created). Do not repair broken `.venv`.
- Baseline: 13 unit files, 90 tests, none run. Run with pytest.
- Add: integration tests (E2E MCP/agent), security tests, performance tests, regression, startup, data integrity.
- Fixtures: safe test DBs (copies, never originals).
- Coverage targets: new behavior must have tests (SP-071).

### DA-14. Documentation and reporting
- Use existing `audits/` and `reports/` dirs; inspect before duplicating.
- Phase-gated deliverables; do not create empty docs in advance.
- Exact paths, evidence, test results in reports.
- Progress record maintained (completed/approved/pending phases, requirements, risks, decisions).
- Never claim unperformed work.

### DA-15. Data protection (15 rules) — enforced across all phases
1. Never delete existing databases.
2. Never reset memory to simplify.
3. Never overwrite historical records.
4. Never drop tables without approved migration.
5. Never replace populated DBs with empty.
6. Back up before schema changes.
7. Transactions wherever practical.
8. Validate migrated counts/relationships.
9. Preserve identifiers.
10. Preserve conversation history.
11. Preserve historical release directories.
12. Never overwrite historical backups.
13. Don't expose credentials/secrets in logs/reports.
14. Don't modify .venv/caches/generated runtime data unless necessary.
15. Never irreversible ops without approval.
- Read-only investigation before writes.

### DA-16. Agent orchestration and delegation
- 12 specialists; selection by complexity/risk/expertise/efficiency.
- Parallel investigations when independent; no concurrent modification of same files.
- Delegation protocol: 9 mandatory fields (objective, paths, scope, may-modify, must-not-modify, deliverables, acceptance criteria, dependencies, read-only vs write-enabled).
- Agents return evidence; Orchestrator reconciles and owns final decisions.
- Reasoning allocation: low/medium/high/extra-high targets per spec §3.4.

### DA-17. Release and versioning
- Version markers reconciled (decision on bump timing).
- Release prep (Phase 12): verify requirements matrix, update docs, release notes, verify startup, verify user data intact, verify config/deps, record unresolved limitations, release checklist.
- No external deployment or overwrite of historical releases without approval.
- Release candidate fully documented and validated before release.
