## Decision 1 — Scope/version interpretation (PENDING)

- **Problem:** Spec titled "SKYFALL v1.0.1" but Phase 2 comparison describes feature scope as "SKYFALL v1.1 — Universal Cloud Intelligence" (Modules 1–11). Spec body does not enumerate modules.
- **Evidence:** Phase 4 §11 (alternatives A–D); Phase 2 §7 (gap sizes Large/Very large); spec §10 Phases 6–12 reference "approved requirements" without defining them.
- **Proposed solution:** Defer to user; document all four alternatives.
- **Alternatives:** A) Literal v1.0.1 patch (process/quality + hardening + UI parity); B) v1.1 Universal Cloud Intelligence (Modules 1–11); C) Hybrid (v1.0.1 = process + hardening + selected modules); D) Re-scope/rename (v1.1 for platform, v1.0.1 for hardening).
- **Trade-offs:** A lower risk/smaller; B matches stated module scope but very large; C balances; D clarifies naming.
- **Migration implications:** None until scope chosen.
- **Backward compatibility:** All options preserve existing data.
- **Security implications:** Larger scope (B) increases attack surface (controlled runner, cloud ops).
- **Tests:** Scope-dependent test plan in Phase 11.
- **Status:** Pending — user decision required before Phase 5/6 feature planning.

## Decision 2 — Modular monolith (no service split)

- **Problem:** Whether to extract services (backend/api.py skeleton implies HTTP service layer).
- **Evidence:** Spec §1 ("prefer modular monolith; no Kubernetes/microservices"); Phase 1 (backend/api.py dormant, no importer).
- **Proposed solution:** Keep modular monolith; backend/api.py remains dormant unless a concrete requirement activates it.
- **Alternatives:** Activate FastAPI service; extract microservices.
- **Trade-offs:** Monolith simpler, lower risk; service extraction adds complexity without need.
- **Migration implications:** None.
- **Backward compatibility:** Preserved.
- **Security implications:** Fewer network surfaces.
- **Tests:** Startup tests confirm single process.
- **Status:** Decided.

## Decision 4 — Table capabilities (sorting/filtering/row actions)

- **Problem:** v0.9.2 and current have 5 read-only, unsorted, unfiltered tables; no sorting/filtering/row actions ever existed.
- **Evidence:** Phase 2 §3 (verified counts); Phase 1 (no setSortingEnabled etc.).
- **Proposed solution:** Preserve read-only metadata posture; add sorting/filtering only where a requirement demands; document decision per table.
- **Alternatives:** Full table rewrite with sorting/filtering/row actions; keep as-is.
- **Trade-offs:** Full rewrite is large and risks regression; minimal change preserves behavior.
- **Migration implications:** None.
- **Backward compatibility:** Preserved.
- **Security implications:** Row actions could trigger cloud ops — require approval gating.
- **Tests:** Table UI tests.
- **Status:** Decided (minimal; revisit if requirement demands).

## Decision 7 — Auth source: MSAL vs Azure CLI (PENDING)

- **Problem:** Canonical v0.9.2 uses MSAL + Environment Management API; current/worktree uses Azure CLI + Power Apps API. No single commit reconciles.
- **Evidence:** Phase 2 §1.2 (re-run correction); Phase 4 (outstanding decision 10).
- **Proposed solution:** Keep both code paths until decided; do not remove either.
- **Alternatives:** A) Canonical MSAL (revert to origin/v0.9.2 auth); B) Current Azure CLI (keep post-baseline).

- **Tests:** Auth flow tests for chosen path.
- **Status:** Pending — user decision required before Phase 7/8 Power Platform work.

## Decision 11 — Migration framework

- **Migration implications:** First migration must be carefully introduced (CI-08).
- **Backward compatibility:** Preserve all records/identifiers.

- **Tests:** Migration tests on copy DBs.
- **Status:** Decided (framework in Phase 8).

## Decision 13 — At-rest encryption of conversation DB

- **Problem:** Conversation messages stored plaintext (H-01).
- **Evidence:** Phase 3 §7.6 H-01; UI labels "not app-encrypted".
- **Proposed solution:** Document plaintext posture now; encryption is a candidate improvement requiring user decision (adds complexity/key management).
- **Alternatives:** Implement SQLite encryption (SQLCipher); document only.
- **Trade-offs:** Encryption protects data but adds dependency and key management; not mandated by spec.
- **Migration implications:** Encrypting existing DB requires migration.
- **Backward compatibility:** Must support reading old plaintext or migrate.
- **Security implications:** Improves at-rest security.
- **Tests:** Encryption round-trip tests.
- **Status:** Decided (document now; implement only if approved).

## Decision 14 — Redaction before persist/export

- **Problem:** add_message stores verbatim; export emits raw content (H-02, M-01).
- **Evidence:** Phase 3 §7.6; Phase 1 (add_message stores verbatim).
- **Proposed solution:** Extend redact_sensitive_text (api_key, connection_string, subscription_key, …) and apply redaction before persist/export.
- **Alternatives:** Redact only on export; redact on persist.
- **Trade-offs:** Redact on persist loses original; redact on export preserves fidelity. Recommend redact on export + optional persist-time scanning.
- **Migration implications:** None.
- **Backward compatibility:** Preserved.
- **Security implications:** Reduces secret leakage.
- **Tests:** Redaction unit tests.
- **Status:** Decided.
