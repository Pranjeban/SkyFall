## 3. Service boundaries and ownership

- **UI:** `MainWindow` owns all pages, dialogs, tables and interactions (`main_window.py:402-539`); `theme.py` owns `APP_STYLESHEET`. No cloud REST or MCP registration lives in UI.
- **Backend/cloud:** `skyfall_cloud/*` owns Azure CLI profiles, Power Platform REST/MSAL, inventories and report writing. There is no active HTTP backend.
- **Workspace:** `WorkspaceManager` owns registry/index SQLite, scanning and consent gates (`manager.py:124-136,164-210,460-520`); MCP tools expose redacted `list_for_ai`/`search_for_ai`/`describe_file_for_ai` (`skyfall_mcp/tools/workspace.py:20-75`).
- **MCP:** `@mcp.tool` functions in `server.py` are the real tool registry; `CapabilityRegistry` validates catalogue metadata and filters enabled entries (`registry.py:44-105`) but does not register tools. `is_tool_enabled` (`:114-118`) has no active caller — a catalogue/tool drift risk.
- **Memory/persistence:** `memory/conversation_store.py` owns conversations/messages; Copilot SDK session state is external, keyed by `copilot_session_id`. Workspace index is a separate store.

## 5. Configuration and error handling

`CapabilityRegistry.default()` loads `configuration/capabilities.json` (`registry.py:93-95`), validates schema/required fields/duplicates (`:44-90`), filters `status=enabled and execution_enabled` (`:97-105`); consumers are `main_window.py:896-903` and `skyfall_mcp/tools/core.py:15-29,64-83`. Model selection is hardcoded `"auto"` (`copilot_service.py:361-370`); no UI model control.

Error handling evidence: MCP logs to stderr only (`server.py:41-42`) to preserve stdio framing; Copilot thread uses `try/except/finally` with status signals (`copilot_service.py:202-232`) and `RuntimeError` on missing SDK (`:234-242`); conversation DB rolls back and closes on exception (`conversation_store.py:69-76`); scan failures stored as errors (`manager.py:514-520`); UI uses `QMessageBox` (`main_window.py:1167-1171,1852-1856`) and an inline label for catalogue failure (`:896-903`).
