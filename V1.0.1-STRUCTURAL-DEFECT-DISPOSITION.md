## 4. Migration / Rollback Procedure Summary

### General Protocol (9-step template per SP-035 / SP-036)

| Step | Action | Notes |
|---|---|---|
| **1** | **Pre-migration snapshot** | Take read-only backup of `Data_Memory/skyfall_memory.sqlite3`; hash with SHA-256; store alongside original |
| **2** | **Environment validation** | Verify Python 3.13 venv is active; all requirements installed; `fastapi`/`uvicorn` available if API route |
| **3** | **Dependency check** | Confirm no downstream modules depend on target migration code path; check import hooks |
| **4** | **Feature toggle / feature flag** | If applicable, flip feature flag to "off" mode; default to pre-migration behavior |
| **5** | **Execute migration** | Run migration script against copy of DB; validate output schema/records |
| **6** | **Post-migration verification** | Run unit suite against migrated copy; compare `export_json()` / schema diff against pre-migration snapshot |
| **7** | **Rollback trigger** | If post-migration verification fails: restore from Step 1 snapshot; re-verify original DB integrity |
| **8** | **Rollback execution** | Restore original `Data_Memory/skyfall_memory.sqlite3` from snapshot; confirm `SELECT count(*)` matches pre-migration |
| **9** | **Approval sign-off** | Record approver sign-off for migration completion; document any residual risks | 

### Per-Migration Rollback Steps (SP-036)

1. **Immediately halt** all further DB writes if migration is in progress
2. **Restore from snapshot** — copy previous `.sqlite3` backup over the current `Data_Memory/skyfall_memory.sqlite3`
3. **Verify integrity** — `sqlite3` `PRAGMA integrity_check;` must return `"ok"`
4. **Confirm no data loss** — compare row counts, schema version, and key fields against pre-migration export
5. **Re-run unit tests** against restored DB; all previously passing tests must pass
6. **Document deviation** — if data cannot be fully restored, file incident report with root cause
7. **Update migration script** — fix root cause before re-attempting migration
8. **Notify stakeholders** — ops, data team, and any consumers of the DB of restore event
9. **Close incident** — record timeline, outcome, and any process improvements

### Data Protection Compliance (SP-025, SP-032, SP-049)
- **No writes to originals** during investigation or migration validation
- All test fixture copies stored in `tests/fixtures/` or temp dirs; originals have `.gitignore` protection (`database/*.sqlite*`)
- Migration scripts must operate on **copies only**; source-of-truth DB remains read-only during investigation
- SHA-256 hashes of original and post-investigation DB must match (verified via `sqlite3` hash or file-level checksum)
